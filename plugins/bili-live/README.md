# B站直播通知插件 1.2.1

独立插件 ID：`bili-live`，只支持 QQ 官方机器人群聊。不依赖 test；test 只保留原来的主动消息诊断／延迟 5 秒发送测试。

## 命令与权限

- `/直播通知 申领`：仅在指定群 `C5A63DEC75FA5ACA12306FA2DAF23FC3` 或 `73DE7E7179ABA7BB8A6E83AEAC89D454` 生效，两群菜单均显示申领按钮。按事件中的 `sender_id` 持久化授权；普通成员也能申领，不要求该群开启主动消息。
- `/直播通知 订阅 房间号`：订阅，也支持 `/主播订阅 订阅 房间号`。
- `/主播订阅 取消 房间号`：取消本群订阅。
- `/主播订阅 列表`：查看本群监听。
- `/直播通知` 或 `/主播订阅`：返回 Markdown 订阅／列表／取消按钮，点击填入输入框，补充参数后发送。指定群额外显示“申领权限”按钮，菜单对该群普通成员开放；其他群不显示申领按钮，也不能执行申领。

申领成功（含重复申领）响应 `现在可以订阅了喵~`。申领只记录权限，不自动创建直播订阅。
未申领就订阅，或在其他群尝试申领，响应：

```text
非常抱歉喵~ 您没有权限，为防止机器人传播至非Eternal Return群 需进行加群领取喵
```

订阅还要求消息发送者是 QQ 事件明确提供的 **群主**，且实时权限查询明确返回 `allow_proactive_msg=true`。
其他群的菜单、列表与取消也保留群主／主动消息权限校验。管理员、普通成员、身份缺失、权限未知、关闭、超时或查询失败不执行；不使用机器人的 `member_role` 充当发送者角色。
群主身份或主动消息权限不满足时返回：

```text
该命令需要身份为群主，并且打开LoMu的主动消息权限(位于LoMu个人资料设置页面)
```

成功响应：

```text
已监听直播间 22669186：等咖啡的人
当前直播中
取消：/主播订阅 取消 22669186
```

首次订阅未开播／轮播房间时状态行显示 `当前未开播`，不发送提醒；已观察到直播中的房间随后转为未开播／轮播时，发送下播提醒。

- **每群只允许订阅 1 个房间**，更换前需取消本群原订阅。
- **每位申领用户全局只允许订阅 1 个房间**；同一个房间可以用于多个自己作为群主的群。更换房间前需取消该用户在所有群中的旧房间订阅。
- 重复订阅不增加额度、不转移订阅人、不重置已发送游标；取消最后一个旧房间订阅后释放用户额度，但保留申领权限。
- 全局最多 50 个不同的有效房间。额度检查与创建／取消在 PostgreSQL 事务锁或 SQLite IMMEDIATE 事务中完成，多个实例并发不能绕过限制。

## 开播／下播提醒

封面图片与下列文字通过 Simbot 合并为一条主动消息，图片下载为字节后上传，不在群消息中显示 HTTP 链接：

```text
已开播！
UP主：等咖啡的人
直播标题：xxx
已开播：1小时 25分钟
直播间：22669186
```

时长由上游真实开播时间与发送时刻计算，B站本地时间按北京时间解析；不足一小时显示分钟，未知／无效／未来开播时间显示“未知”，不伪造时长。
封面不可用时保留文字并标明“封面暂不可用”，不发送替代图片链接。

检测到下播（直播状态 `1 -> 0/2`）时，仍将封面图片与下列文案通过 Simbot 合并为一条主动消息：

```text
已下播喵~
UP主：等咖啡的人
直播标题：xxx
直播时长：1小时 25分钟
直播间：22669186
```

下播时长使用本群保存的本场开播时间，到首次发现下播的时刻估算（不是上游提供的精确结束时间）。上游下播时清空／重置开播时间不会影响计算；缺失、无效或未来开播时间仍显示“未知”。暂停轮询、权限关闭或查询退避可能增加检测延迟，不能还原暂停期间的精确下播时间。

## 轮询与去重

- 首次成功订阅正在直播的房间，立即使用本次查询结果异步补发开播提醒，不再等待下一分钟的轮询，也不额外查询 B站。订阅确认不等待主动发送完成；权限复查、封面上传及必要的发送间隔仍可能带来短暂延迟。
- 补发任务跟随插件生命周期停止；尚未消费的待补发游标由后续轮询恢复。重复订阅不重置游标，重载／重启不重复补发；未开播／轮播不补发开播消息。
- 每分钟第 20 秒轮询，与 group-pet 1.2.3 的第 5／35 秒错峰；后台状态请求通过宿主公共锁串行，慢查询不重叠。
- 仅轮询已绑定申领人的订阅；轮询前还检查群主动消息权限，未知／关闭的群不查询、不消费游标；恢复开启后继续。单批权限检查短暂复用，超过 30 秒重查。
- 同房间多群订阅只查询一次，封面扇出复用；UP 名称缓存一小时。错误按 2、4、8、16、32、60 分钟退避。
- 发送前持久化场次 CAS，失败／超时不重发本场，优先避免重复；首次补发与常规通知共用 6.1 秒发送间隔，等待间隔或权限未确认时不消费游标。不承诺外部平台 exactly-once。
- 下播状态变更与 `bili_live_ended` 去重记录在同一事务中提交；同一群、同一房间、同一已知场次的下播只尝试发送一次，状态抖动和重载不重复提醒。上游没有可用场次时，按观察到的状态转换 CAS 去重，无法跨未知场次判断是否为同一场。
- 未开播／轮播持续轮询不重复发下播，`0 <-> 2` 也不发；下播通知遵循原申领绑定、主动消息权限、群发送间隔和失败去重规则。

## 数据与升级

复用主程序的 PostgreSQL 或 SQLite。为无损接管已部署 test 1.8.0 的订阅，沿用 **`test_bili_live`** 表及原游标，不清空、不重建表、不重置已发送场次。
表名只是兼容遗留名，数据和轮询归本插件所有；test 1.9.0 不再访问该表。
新增 `bili_live_claims(sender_id)` 保存申领用户，`bili_live_bindings(group_id, room_id, sender_id)` 保存每群唯一的有效订阅及订阅人；业务读写均使用 Ktorm DSL。
遗留数据没有可验证的订阅人，**升级后暂停轮询，不自动授予申领权限**。群主申领后重新订阅一个房间即可绑定并恢复该房间；原发送游标不重置，其他历史记录保留但不轮询，可通过列表查看并取消。

1. 备份旧插件／数据库，先热更新 test 1.9.0，确认旧直播 worker 已停止。
2. 安装 bili-live 1.2.1 后启用本插件；群主先在任一指定群申领，再回自己的群重新订阅一个房间，后续订阅仍须满足群主及主动消息权限。
3. 无需替换 core 3.0.3。不要在 bili-live 启用时回退到带直播轮询的旧 test；回退前先停用 bili-live，保留数据库。

构建：`./gradlew :plugins:bili-live:test :plugins:test:test stageCommandPlugins verifyVersions`。
产物：`plugins/bili-live/build/libs/bili-live-1.0.0.jar`、`plugins/test/build/libs/test-1.0.0.jar`（逻辑版本 1.9.0）。
业务数据操作使用 Ktorm DSL，建表脚本位于 `src/main/resources/sql/`。

## 推送次数

- 从 1.1.1 起记录 QQ 接口明确返回成功的主动直播通知，每条消息计 1 次；同一房间向多个群成功发送分别计数，首次直播补发也计入。
- 从 1.2.0 起成功的下播通知也计入同一直播推送累计次数。订阅确认、手动查询、无变化轮询、关闭权限、图片生成失败、发送失败或超时均不计数；不推算升级前的历史次数。
- `qq_push_statistics` 按 `push_kind=bili-live`、`group_id`、`subject_id`（规范房间 ID）保存 BIGINT `push_count`，可按房间汇总所有群或单群查询。统计复用主程序数据库，SQLite 默认在 `data/lomu.db`，PostgreSQL 使用主程序的连接池和 schema。
- `qq_push_receipts` 保存成功发送的独立记录 ID、对象和时间；回执去重与次数递增在同一事务内，数据库重试不重复计数，并发递增不丢失。
- 取消／重新订阅或重载／重启不会清空累计次数，不向群消息额外附带统计文字。统计写入失败最多重试 3 次并记录日志，不因此重发 QQ 消息；外部发送与本地事务无法原子提交，进程在二者之间崩溃可能漏记。
